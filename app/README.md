# 迷雾工具箱 · app

自用的《黎明杀机》中文工具站。移动端优先，部署 Cloudflare Pages。

方案文档：`../docs/dbd-tool-site-plan.md`
设计稿：`../design/ui-draft-v9-final.html`
渲染截图：`../design/renders/`

## 跑起来

```bash
npm install
npm run dev         # http://localhost:5173
```

Vite 配了 `host: true`，手机连同一局域网可用 `http://<电脑IP>:5173` 真机调试。

```bash
npm run typecheck   # tsc --noEmit
npm test            # 检索逻辑单测（13 个用例，含全部 99 个角色自检 + 多选筛选 AND）
npm run build       # 产物在 dist/
npm run preview     # 预览构建产物
npm run verify      # 产物自检（引用完整性 / 数据自洽 / 体积），build 之后跑

npm run import      # 重新导入全量数据 + 图标（图标自动转 WebP）
npm run import:no-icons   # 只导文本
npm run import:portraits  # 只导角色头像
npm run to:webp     # 存量 PNG → WebP 迁移（一次性，可重复跑）
```

> 本机三个坑：`npm.ps1` 被执行策略拦，要用 `npm.cmd`；
> npm 默认缓存目录在工作区外会被沙箱拒绝，需 `$env:npm_config_cache = "$PWD\.npm-cache"`；
> Node 测试跑器 spawn 子进程会 EPERM，必须带 `--test-isolation=none`。

## 数据从哪来（重要）

| 内容 | 来源 | 授权 |
|---|---|---|
| 技能 / 配件的**中文文本、稀有度、归属** | [迷雾笔记 dbdwiki.com](https://dbdwiki.com) 的公开 JSON | **CC BY-NC-SA 4.0** |
| **图标**（1201 个）与**角色头像**（97 个） | [deadbydaylight.wiki.gg](https://deadbydaylight.wiki.gg) | 游戏素材，权利归 Behaviour |

**为什么不用 wiki.gg 的数据表**：wiki.gg 只有 de/es/fr/it/pl，**没有中文**，
`Module:Datatable` 全英文。中文内容只能另找来源。

**CC BY-NC-SA 4.0 的约束（必须遵守）**：
- **NC 非商业** —— 不挂广告、不收赞助、不做付费内容
- **BY 署名** —— 站点底部信息区已固定署名 + 协议链接，别删
- **SA 相同方式共享** —— 衍生整理也要用同样协议

## 数据形态

```
public/data/
├─ owners.json                    99 位角色，含 counts / pinyin / initials / avatar
├─ perks/{killer,survivor}.json   该阵营全部技能（330 条）
├─ addons/{ownerId}.json          单个屠夫的配件（46 个文件，901 条）
└─ addons-index.json              901 条配件的轻量检索索引（不含描述）
```

分包实测：`owners.json` 17.7KB、`perks/killer` 82.3KB、`perks/survivor` 98KB、
单个屠夫配件约 10KB。角色总览只需 owners.json。

### `flavor` 与描述正文的区别（很重要）

条目有两个不同的文本字段，别混：

| 字段 | 含义 | 渲染位置 |
|---|---|---|
| `description[]` | 效果说明，一条一段 | 抽屉正文（`·` 开头的走缩进列表样式） |
| `flavor` | 游戏内的「风味文本」，**不是每个条目都有** | 抽屉**底部**单独的斜体衬线块 |

- 有 flavor 的条目（多数来自迷雾笔记的数据）在 `flavor` 里**自带引号**，直接渲染。
- 没有 flavor 的条目 `flavor` 为空字符串，底部那块不出现。
- **不要把第一段正文误当成 flavor**：断魂小丑那 20 件附加品，游戏里第一段
  （如「虐待倾向，惊悚血腥，令人震惊……」）属于**描述正文**，不是引用文本，
  所以并进了 `description[0]`、`flavor` 留空。反过来把带引号的引用塞进
  `description` 也会让排版和游戏内顺序对不上。

**判断依据**：迷雾笔记的数据里 flavor 单独成字段；wiki 表格里 `{{quote}}` 生成的
`<i>` 斜体行才是 flavor，非斜体的 `<li>` 是效果正文。

### 跨角色搜索为什么要有 `addons-index.json`

配件按角色分包，总览里跨角色搜配件时不可能去下载 45 个分包（合计 **471KB**）。
所以构建期额外产出一份轻量索引（901 条，**348KB → gzip 约 103KB**），
在总览**第一次打开搜索**时按需加载一次。

索引字段：`id / ownerId / title / titleEn / rarity / icon / pinyin / initials / text`。
其中 `text` 是该条目描述正文去掉标点后的纯文本，用来支持**按效果搜索**
（输入「疲劳」「无法侦测」「发电机」等能命中提到该效果的条目）；
`titleEn` 是从 wiki 补齐的英文名，让总览也能用英文搜配件（如 `Iridescent`）。

技能不需要索引 —— 它们本来就按阵营整份加载（`perks/{side}.json`），
描述正文在客户端用 `normText()` 现算一次并缓存（`perkTextById`）。

**体积取舍**：曾对比过「只在索引里存 34 个效果词的倒排」（gzip 仅 7.6KB），
但它只能搜固定词表；选了体积大 90KB 的全文方案，换来「任意效果词都能搜」。

**结果截断**：搜「逃生者」这类泛词会命中几百条，跨角色结果一次最多渲染 60 条，
超出时在底部提示「还有 N 条未显示」。

### 快捷筛选 chip（`FILTER_TERMS`）

搜索框下方一排 **18 个效果词**，**可多选**：点一下选中，再点一下取消。

- **多选是 AND（同时满足）**，不是「或」。例：同时选 `无法侦测` + `图腾`
  → 只剩 2 条：厄咒：毁灭序曲、秘密项目。
- chip 与输入框关键词也是 AND：关键词还管名字/拼音，chip 只管效果正文。
- 一旦选了 chip，结果区**只列条目（技能/配件）、不列角色** ——
  角色没有效果正文，硬筛会把 44 个杀手全铺在前面，真正想找的技能被挤到几屏之后。
- chip 已选中的状态用 `aria-pressed` + 高亮描边/底色表示，不额外加计数。
  **选中态刻意不加粗**：加粗会让 chip 自身变宽，换行布局下会把刚点的那个词挤到下一行。

词表按**实测命中量从高到低**排序（构建期用真实数据统计的技能+配件命中总数）：

| 词 | 命中 | 词 | 命中 | 词 | 命中 |
|---|---|---|---|---|---|
| 气场 | 276 | 急速 | 57 | 血祭品 | 23 |
| 发电机 | 127 | 图腾 | 46 | 出口大门 | 22 |
| 治疗 | 99 | 翻越 | 45 | 致盲 | 13 |
| 恐惧范围 | 98 | 疲劳 | 43 | 恩赐 | 8 |
| 受伤 | 76 | 无法侦测 | 43 | | |
| 破坏 | 63 | 钩住 | 42 | | |
| | | 钩子 | 29 | | |
| | | 厄咒 | 24 | | |

杀手/人类分侧命中数（`killer / survivor / addons`）差异很大，例如：
`气场 48/71/157`、`图腾 25/21/0`、`无法侦测 11/0/32`、`厄咒 22/2/0`、`恩赐 2/6/0`。
配件那一列就是「人类页为什么没有 `无法侦测`」的原因 —— 那个词只在杀手侧有正文命中。

`钩子` 是 `天灾钩子` 的**上位词**：6 条天灾钩子技能的标题里都带「钩子」，
所以用 `钩子` 一次覆盖天灾钩子系列 + 普通钩子相关（29 条 vs 7 条）。
它和 `钩住` 也不冗余 —— 杀手侧 `钩住` 28 条、`钩子` 10 条，重合只有 4 条。

**人类页会自动隐藏 0 命中的词**（目前只有「无法侦测」：人类技能 0 条）。
判定用的是当前阵营已加载的技能描述，不依赖配件索引，所以不会出现「先隐藏后突然出现」。
切阵营时已选中但新阵营不可用的词会被自动剔除（词表为空 = 还在加载 → 不剪，避免误清空）。

**刻意没放进词表的**：

- `修理`、`冷却` —— 支配它们的其实是别的东西：修理基本被 `发电机` 覆盖，
  冷却 121 条里绝大多数是配件且语义太窄，收益低于占位成本。
- `柜子`、`一触即死`、`加速`、`献祭`、`地道`、`坚忍` —— 实测各只命中 0~3 条，放进去点了基本是空结果，只会误导。

chip 行是**自适应换行**（`flex-wrap: wrap`），不用横向滚动：18 个词在 360px 宽下
一排约放 5 个，排成 **5 + 5 + 5 + 3 四行**，整块高约 **131px**。
行距 6px 比列距 7px 略小，看起来更像一整块词云而不是散开的行。
索引里的 `id` 必须和分包条目一致，否则「点搜索结果 → 落地后自动打开抽屉」
的 focus 查找会失败。构建脚本里对 `addon:` 前缀做了幂等处理（源 id 已带前缀）。

### 滚动位置的复位规则

`.main` 是唯一的滚动容器，总览/钻取/搜索结果都在它里面滚，所以三件事必须分开管：

| 场景 | 行为 |
|---|---|
| 打开搜索 | 主区**回到顶部**（先把当前位置存进 `beforeSearchScroll`） |
| 关闭搜索 | 回到打开搜索之前的位置，不丢浏览进度 |
| 切换阵营 | 回到顶部，并清掉该阵营记住的位置 |
| 进入角色（钻取） | 回到顶部 |
| 返回总览 | 恢复该阵营上次的位置 |

两个坑：

- 搜索态滚动的是**结果列表**，所以 `handleScroll` 在 `searchOpen` 时直接 return，
  否则会把结果列表的滚动位置写进「总览记住的位置」，返回总览时落到奇怪的地方。
- 路由变化时要把 `beforeSearchScroll` 清零。否则「关闭搜索后还原」会和
  「进入角色回到顶部 / 返回总览恢复位置」抢同一帧，把滚动位置设回上一个搜索会话的值。

### 从搜索页点进角色，返回时要回到搜索页

路由一变就会清空搜索态（`setQuery('')` / `setActiveChips([])` / `setSearchOpen(false)`），
所以「搜了内容 → 点进某个角色 → 返回」原本会落到一个空的总览。现在用一个 ref 记住：

| 场景 | 行为 |
|---|---|
| 搜索（有关键词或筛选词）→ 点角色 → 返回 | **回到搜索页**，关键词与筛选词都在 |
| 搜索（空）→ 点角色 → 返回 | 普通总览（没有内容可还原） |
| 总览 → 点角色 → 返回 | 普通总览，滚动位置还原 |
| 搜索 → 切换阵营 | 搜索态与记忆一起清空（搜索词是按阵营算的） |
| 深链 / 刷新到角色页 → 返回 | 退回该阵营总览 |

三个实现要点：

- **记忆只还原一次**（还原后立刻置 null）。否则之后任何一次「从角色页返回」
  都会莫名其妙回到上一次的搜索结果。
- **还原时不自动聚焦输入框**。`SearchBar` 的 `autoFocus` 由 `searchAutoFocus`
  控制：还原时为 `false`，用户主动点搜索按钮时为 `true` ——
  否则一返回手机就弹起键盘，直接挡住半屏结果。
- **返回键走 `history.back()` 而不是重新 `navigate`**（`arrivedFromOverview` ref 判定）。
  否则「搜索 → 角色 → 返回」会压进一条新历史，再按一次系统返回又回到刚才那个角色页。
  直接深链进来（没得 back）才退回总览。

## 图片资源：全部转 WebP，分三档参数

wiki 只提供 PNG，1300 张透明图合计 **20.7MB**。杀手总览一次要拉 45 张人像
（PNG 平均 48.9KB → 单页 **2.2MB**），这是首屏最贵的一笔开销。

现在全部落盘 WebP，合计 **12.5MB**；但**三档素材用的编码参数不同**，
因为踩过的坑完全不同 —— 随便统一成一个档位就会出问题：

| 素材 | 数量 | 参数 | 相对 PNG | 实测差异（只统计 alpha≥16 的可见像素） |
|---|---|---|---|---|
| 条目图标 128px | 1201 | `nearLossless` | −28% | 最大色差 **2** |
| 角色抠图 200px | 97 | `nearLossless` | −63% | 最大色差 **2** |
| 卡片框 198×241 | 2 | `lossless` | −41% | **0**（解码后逐字节一致） |

**为什么都不用普通有损（q92）**：实测过，两个独立的原因 ——

- **角色抠图**：q92 平均色差 5.6、最大 117；换 4:4:4 不采样只到 5.5，提到 q95 还有 5.0。
  都是能看出来的糊边。nearLossless 直接把最大色差压到 2。
- **条目图标**：q92 最大色差 10（比 nearLossless 差 5 倍），体积反而**更大** ——
  `bloodyCoil` q92 11.7KB vs nearLossless 8.0KB。平面色块 + 硬边的游戏图标经不起色度采样，
  有损档白丢质量还没换来体积。
- **卡片框**：大面积平滑渐变，q92 在暗底上能看出色带，所以走无损。

**两个测量陷阱**（写在这里免得下次再踩）：

1. **必须排除 alpha<16 的透明像素**。透明区的 RGB 是未定义值，
   直接逐像素比会得到「最大色差 255」这种假报警，把结论带偏。
2. **在原始尺寸上比，比在显示尺寸上比更可靠**。缩放插值会把差异重新摊开，
   算出「92% 的像素都不同」这种没有指导意义的数字。

### 人像：只用 200px 母版（响应式试过，已回退）

线上实测原来的一次：`JS+CSS ~110KB（gzip）` + `owners.json ~4KB` + **`人像 40 张 1092KB`**
—— 首屏 75% 的流量在人像上，原因是**尺寸错配**：手机上角色卡 6 列，人像只显示
≈63 CSS px，却在下载 200×200 的图。

**做过三版响应式（`srcset` + `sizes` + `@96/@144/@180` 三档变体），最终整套回退了**：

| 版本 | iPhone 首屏人像 | 采样率 | 结果 |
|---|---|---|---|
| sizes=69px（满采样） | 963KB | 106% | DPR3 算成 207 → 落到母版，等于没优化 |
| sizes=48px | 325KB | 76% | 省得多，但**明显偏软** |
| sizes=56px + 新增 `@180`（q92） | 505KB | 95% | 折中，仍然「显示效果差太多」 |

回退原因：小图档都是有损重编码，**观感劣化比省下的流量更明显**。人像是这个站的主视觉，
优先级放在画质上。所以现在所有设备都走同一张 **200px nearLossless 母版**。

**如果以后要再优化首屏，这些数据仍然有效**：

- 单纯压人像不可行：nearLossless 在 200px 是 24.1KB/张，`@180` 用 nearLossless 还要 18.9KB
  （iPhone 首屏 754KB，相对 963KB 只省 22%），省不动；有损档则会伤观感
- 更值得走的方向（都不是压小图片）：
  1. **Service Worker 缓存** —— 第二次访问接近 0 网络，这是 GitHub Pages 上唯一能绕开
     「所有文件只有 `max-age=600`」的办法
  2. **Cloudflare 反代 / 迁回 Cloudflare Pages** —— 能自己发 `Cache-Control: immutable`
  3. **雪碧图** —— 首屏请求数 40 → 1，字节数基本不变，但对中国移动网的高 RTT 有效
- 测量的两个陷阱见上一节（透明像素、比较尺寸）

`verify-assets.mjs` 的 `[3b]` 现在反向守住这件事：**dist 里一旦出现带 `@尺寸` 后缀的人像变体就报错**，
避免残留文件白占体积又没人引用。

**GitHub Pages 的缓存限制**：它对所有文件只发 `cache-control: max-age=600`，
而且**不支持自定义响应头**（没有 `_headers`）。所以哪怕文件名带 hash 也拿不到
`immutable`，第二次访问仍要重新下载/校验。想彻底解决只有两条路：
换到能设响应头的托管（Cloudflare Pages + 自定义域名），或加 Service Worker 自己缓存。

编码参数这三个地方必须一致，否则「重新导入」和「存量转换」的产物质量会不一样：

- `scripts/import-dbd.mjs` 的 `WEBP_OPTIONS`（条目图标）
- `scripts/import-portraits.mjs` 的 `WEBP_OPTIONS`（角色抠图）
- `scripts/to-webp.mjs` 的 `ICON_WEBP` / `PORTRAIT_WEBP` / `LOSSLESS`（按路径分档）

`npm run to:webp` 是存量迁移脚本：转码 → 校验尺寸与透明通道没丢 → 改写 `public/data`
里的 `.png` 引用 → 核对每个引用都能找到文件 → 删掉原 PNG。
先跑 `--keep` 留一份 PNG 对照，确认没问题再跑一次（不带 `--keep`）只删 PNG。

## 网页端适配（≥900px）

移动端是基准，**所有桌面规则都锁在 `@media (min-width: 900px)` 和
`@media (hover: hover) and (pointer: fine)` 里**，手机上的表现一个像素都不变。
断点选 900px 的理由：iPhone 横屏 844px、iPad 竖屏 820px 都还走移动端布局，
iPad 横屏 1180px 才切桌面。

| 项目 | 移动端 | 桌面端 |
|---|---|---|
| 容器 | 满宽 | `max-width: min(1360px, 100% - 64px)` 居中，两侧至少留 32px |
| 两侧 gutter | — | 两层光晕（跟随阵营色）+ 1px 骨白「发光接缝」，见下 |
| 搜索态 | 满宽 | 满宽（与移动端一致，只是左右留白多一点） |
| 角色网格 | 固定 6 列 | 900~1279px 自适应（7~11 列）；**≥1280px 锁定 12 列** |
| 技能网格 | `auto-fit minmax(68px)`，3 条自动撑满一行 | 固定 104px 列宽 + 左对齐 |
| 配件网格 | 固定 5 列 | `auto-fill minmax(96px, 1fr)` |
| 结果列表 | 满宽 | `max-width: 760px` 居中，**条目整体放大**（见下） |
| 底部 Tab | 满宽条形，两个 Tab 各占一半 | 同一套，只把图标/字号放大一档（22px / 12px） |
| 抽屉 | 满宽贴底 | `max-width: 720px` 居中卡片，仍从底部滑入 |
| 底部信息 | 跟在角色网格后面 | 内容不满一屏时用 `margin-top: auto` **贴到容器下沿** |
| 字号 | 正文 13.5px / 小字 10~11.5px | 正文 15.5px（抽屉）/ 18px（搜索结果）｜顶栏标题 19px、详情标题 21px｜小字统一提一档 |
| 焦点 | — | `:focus-visible` 红色描边（触摸不会触发，对手机无影响） |
| 悬停 | — | 卡片描边、图标格上浮 2px、行底色、链接变亮 |

**字号为什么要单独提一档**：桌面的视距比手机远得多，手机上「一眼扫过」的
10~11.5px 小字（顶栏副标题、筛选词、来源说明）在 1080p 显示器上明显吃力。所以桌面不只是
把正文放大，而是**逐个查过每一处小字**：

| 位置 | 移动端 | 桌面端 |
|---|---|---|
| 搜索结果标题 / 副标题 | 13.5 / 11px | **18 / 13.5px** |
| 搜索结果缩略图 | 40px（角色卡 38、技能缩略 34） | **54px（50 / 42）** |
| 抽屉正文 / 列表项 | 13.5 / 13px | **15.5 / 15px** |
| 详情标题 / 英文名 | 19 / 10px | **21 / 11px** |
| 技能·配件名称 | 9.5px | 11.5px |
| 快捷筛选词 | 12px | 13px |
| 来源说明 / 落款 | 11 / 10px | 12.5 / 11px |

**两侧 gutter 的处理**（大屏上不想要两条纯黑）：

1. `body` 叠两层极淡的 `radial-gradient`（顶部冷色天光 + 中栏反光），
   `background-attachment: fixed`。中栏背景不透明，所以这两层只在中栏**之外**可见。
   反光那层用 `var(--glow-body)`，跟着阵营换色。
2. `.app` 加四层 `box-shadow`：两圈彩色模糊（120px / 36px）贴着栏边往外散，
   外加 `1px 0` / `-1px 0` 两圈零模糊的骨白，形成一条「被打亮的接缝」。
   偏移阴影的好处是**与视口宽度无关**，任何屏幕上都正好贴着栏边。

实测（1920px 视口，模拟叠加结果）：紧贴栏边约 `rgb(40,14,15)`，
向外 96px 处已衰减到 `rgb(15,7,9)`，160px 外基本回到底色 `rgb(6,6,8)`。
觉得光太强/太弱就调 `.app` 的 box-shadow 两个 alpha（0.14 / 0.09）。

**列数换算**（`min(1360px, 100% - 64px)` 容器，10px 列间距）：

| 视口 | 列数 | 栏宽 | 卡片 | 单侧 gutter |
|---|---|---|---|---|
| 1024 | 8 自适应 | 960 | 107px | 32px |
| 1180 | 10 自适应 | 1116 | 99px | 32px |
| 1280 | **12 锁定** | 1216 | 89px | 32px |
| 1440 | **12 锁定** | 1360 | 101px | 40px |
| 1920 | **12 锁定** | 1360 | 101px | 280px |
| 2560 | **12 锁定** | 1360 | 101px | 600px |

**踩过的五个点**：

- **技能网格不能用 `auto-fit`**。`auto-fit` 会折叠空轨道，3 条技能在桌面会被拉成
  各占 1/3 屏宽的巨幅菱形。桌面改用 `repeat(auto-fill, 104px)` 固定列宽。
- **12 列要单独钉死**。`auto-fill` 只能保证「至少 N 列」，具体几列随宽度浮动
  （同一台机器拉宽窗口会从 11 列跳成 12 列）。要「永远 12 列」得在 ≥1280px 用
  `repeat(12, minmax(0, 1fr))`，让宽度只影响格子大小。
- **`.sheet` 的桌面居中只能改 `max-width` / `margin-inline`**。
  拖拽关闭时 JS 会直接写 `style.transform`，在媒体查询里加 `transform`
  会在手指一动就被覆盖掉，抽屉会跳回满宽。
- 悬停用了 `:not(:active)`：否则鼠标按下时 hover 的上浮会盖掉 `.cell:active` 的缩放。
- **底部信息要贴底，必须给 `.main` 的每个子项写 `flex: none`**。
  只在 `.foot` 上写 `margin-top: auto` 而忘了这条，`.main` 变成 flex 容器后
  其余子项会被 flex 压缩（`.chargrid` 的行高会被挤扁）。

**已知取舍**：角色卡在被图源卡住 —— 人像源图只有 200×200，卡片头像按 124% 显示。
12 列下面卡片约 101px、头像约 125 CSS px，DPR1 桌面是缩小（很清晰），
DPR2 的 Retina 上会被放大 1.25 倍（略软）。要在 Retina 上更锐，
把 `scripts/import-portraits.mjs` 的 `iiurlwidth` 从 200 提到 300 重跑一遍即可
（人像总量会从 2.3MB 涨到约 4MB）。

## 角色卡片：单层烘焙底 + 竖长方形外框

wiki 首页 `<div class="dbd-main-character-roster">` 里每张卡原本是三张底图叠出来的
（`charPortraitShadowBG` + `charPortraitBg` + `charPortraitRoleBg`），底图本身是 250×250，
**实体卡片只占 x 25\~222 / y 5\~244（约 198×241，比例 0.822）**，四周全是透明留白。

所以做了两步：

1. **构建期把三层合成并染色**成静态图（`frame-killer.webp` / `frame-survivor.webp`）
2. **裁掉透明留白**（`scripts/crop-frames.mjs`）→ 198×241，卡片正好填满格子

> `crop-frames.mjs` 的输入必须是 **headless Chrome 直接烘焙出来的原图**，
> 而且只做一次 `extract`。别用「合成到新画布」的方式重建原图来测试 ——
> 合成会做 alpha 预乘，半透明的柔和阴影被舍入一次就回不来了（实测文件从 34.8KB 掉到 17.7KB，
> 掉的那一半正是阴影渐变）。

结果运行时只有**一个背景图层** `.char__frame`，`background-size: 100% 100%`，
`--char-ratio: 198 / 241`。

- **外框是竖长方形**（56×68px），6 列
- **头像保留 wiki 原始 512×512 正方形画布（不裁边）**，按固定宽度等比缩放，底部对齐：

```css
.char__av img {
  position: absolute;
  left: 50%;
  bottom: 0;
  transform: translateX(-50%);
  width: 124%;
  height: auto;
  display: block;
}
```

**为什么用原始画布而不是裁到内容**：
裁边后各角色的内容宽高比从 0.67 到 1.03 不等，无论按固定宽还是固定高都必然导致大小不一；
而**保留统一的正方形画布 = 所有角色共享同一尺度**，这正是 wiki 名册看起来一致的原因。

**为什么 width 是 124%**：画布四周是透明留白（实测内容只占 **72.5% 宽 × 88% 高**），
所以可以让画布溢出格子、由 `.char__av` 的 `overflow: hidden` 裁掉，角色内容随之放大。
124% 是实测的安全上限（格子 56×68px）：

| width | 内容占卡片 | 最小余量(左/上/下) | 裁切 |
|---|---|---|---|
| 110% | 78% / 79% | 4.9 / 8.9 / 2.8 | 无 |
| **124%** | **88% / 90%** | **2.0 / 1.3 / 3.1** | **无** |
| 126% | 89% / 91% | 1.5 / 0.3 / 3.2 | 无（但头部只剩 0.3px 余量）|
| 128% | 91% / 93% | 1.1 / −0.8 / 3.2 | **16 个角色头部被切** |

- **杀手红底、求生者蓝底**（颜色已烘焙进图里）

### ⚠️ iOS Safari：运行时不能用 CSS 滤镜

wiki 的染色参数是 `sepia(1) saturate(30) hue-rotate(289.1deg) saturate(7) brightness(0.47)`
这种极端滤镜链，**iOS Safari 上会渲染异常** —— wiki 自己的 CSS 里就写着 `/* doesnt work :( */`。

所以全部改成**构建期烘焙**（用无头 Chrome 渲染成静态 PNG），运行时零 `filter`。
角色图的 `drop-shadow` 也去掉了。全站只剩 3 处 `backdrop-filter: blur()`（顶栏/底栏毛玻璃）。

两个烘焙用的临时页面在 `public/bake*.html`（用完即删），
底图源文件在 `scripts/assets/card-source/`（**不在 public 里**，避免被部署）。
重新烘焙的流程：三张底图叠加 → headless Chrome 截 250×250 → `npm run crop-frames` 裁成 198×241 无损 WebP。

**角色清单来自首页名册**，不是 `Category:Character Selection Icons`：
名册有 110 条（50 杀手 / 60 求生者）、100 个唯一图片，**覆盖全部角色包括最新的**
（`K41 TheKrasue` … `K45 TheTerrifier`、`S43 LaraCroft` … `S55 SiennaShaw`）。
分类里只有 76 个，最新那批完全没有 —— 这就是之前 21 位对不上的真正原因。

匹配结果：**97/97 全部命中**，无一位走降级。

蓝色不是随便挑的：把 `frame-{side}.webp` 两张烘焙底图取样，杀手底是 H355°（红），
逃生者底是 H205°，所以蓝取了同色的**高饱和石板蓝**，和卡片底一起看不打架。

实现要点：

- 切换靠 `html[data-side='survivor']` 这一个选择器覆盖变量（`styles/tokens.css` 末尾），
  没有第二套类名，组件里不用判断阵营。
- `data-side` 由 `pages/Browse.tsx` 的 `useEffect` 写；但**深链接（`#/survivor/...` 直接打开）**
  首帧会先按杀手红渲染，闪一下才变蓝。所以 `src/main.tsx` 在 `createRoot().render()` **之前**
  又按 `location.hash` 先判了一次。两处重复是有意的，别删掉 `main.tsx` 那次。
- 主题色落到的位置：顶栏标题下的小字、顶栏/搜索框底部的 1px 渐变线、底部 Tab 的滑块与光带、
  桌面端两侧 gutter 的 `.app` box-shadow。
- **`--glow-*` 是桌面专用的**，手机端 `body` 的 radial 和 `box-shadow` 都不会显形，
  换色对移动端唯一的可见变化就是强调色本身。

**Tab 切换动画**：`.tabbar::before` 是一块占一半宽、用 `translateX` 滑动的底（0 / 100% 两档），
`.42s cubic-bezier(.22,.61,.36,1)` 缓出；`::after` 是一条 26px 的柔光带跟着一起滑，
选中的 Tab 图标 `translateY(-1px) scale(1.06)` 轻微上浮。

桌面端**完全沿用这一套**（满宽条、两个 Tab 各占一半、光带仍是 `width: 50%`），
只把图标和字号放大一档（22px / 12px），别的什么都不用改。
**别改回浮动药丸**：那是更早的一版（`max-width: 320px` + `border-radius: 999px` +
内嵌药丸滑块），脱开了底边、和顶栏毫无呼应，丑。

## 首屏加载动画（`index.html` 内联的 `#splash`）

一段雾里的加载画面，参考《黎明杀机》对局载入时的观感。主体是游戏那个**「计数划痕」标记**：

```
     │     │     │     │    四条竖线：x = 19 / 40 / 61 / 82（间距 21，线宽 7，间隙 14）
     │     │     │     │    左右两根 y 10→92（长 82）
     │     │     │     │    中间两根 y 6→96（长 90，只比左右长一点，两端各差 4）
      ╲                  一条斜线：左上 (-2,36.5) → 右下 (102,64.5)，约 15°，横穿四条
```

这个标记在设定上是「四个逃生者 + 一个屠夫」：四条竖血痕 + 一条斜痕（原图每条竖痕顶端
还压着骷髅，这里简化掉了）。所以形状按这个读法取：

- **整体接近正方形**（画满约 111×97，显示 112×112）；
- 四条竖线细而高、彼此留得开（线宽 7、间隙 14），像一组血痕而不是四根柱子；
- **中间两根比左右两根长一点**（中间 90、左右 82，两端各差 4）—— 差别是收着的，不是共用一条基线那种「中间戳出来」；
- 斜线**从左上划到右下**，只有 **~15°**，两端探出画布左右边缘 —— 它在四条竖线上的落点
  从左边的 y≈42 到右边的 y≈59，是最后才划上去的那一笔（= 屠夫）。

五条笔画**依次被「划」上去**（一笔接一笔，每条 0.31s、彼此错开 0.19s），
全部划完后短暂停留 → 整组淡出 → 从第一条重新开始。标志本身是**纯白**（`#e8e2d6`），
和游戏 logo 一致（黑底白标 / 白底黑标，都是单色）；背后是两层各自漂移的血色雾。
**画面上没有任何文字** —— 只有这个标记，所以它也不受字体加载影响。

### 「划」是怎么画出来的

每条 `path` 上写了 `pathLength="1"`，把自身长度归一化成 1，于是所有笔画共用
`stroke-dasharray: 1; stroke-dashoffset: 1 → 0` 就够了 —— **生长速度与线条长短无关**，
不会出现斜线先画完、竖线还在半路。方向由 `d` 的书写顺序决定：
竖线写 `M19 10V92`（**由上往下**），斜线写 `M-2 36.5L102 64.5`（由左上往右下）。

五条笔画各有一套 keyframes（`sp-line-1` ~ `sp-line-5`），只是时间窗不同：
`0→13 / 8→21 / 16→29 / 24→37 / 32→45 %`（整轮 2.4s）。
淡出挂在**整组** `.sp-tally` 上（86% → 93%），所以是「整块标记消失」而不是一条条褪掉；
100% 时 dashoffset 复位，下一轮从空白的雾里重新划起。

动画只用 `transform` / `opacity` / `stroke-dashoffset`，**不用任何滤镜**（iOS Safari 的老问题）。
系统开了「减少动效」时动画全停，但会额外把 `stroke-dashoffset` 强制归零，
否则停在初始值上整块标记都看不见。

### 为什么写死在 `index.html` 里，而不是做成 React 组件

它是**为了掩盖等待**而存在的，所以必须比 JS 包更早出现。写成组件的话它自己也要等 JS —— 就没有意义了。
内联之后它是 HTML 的一部分：**零外部请求**，浏览器解析完 `<head>` 就已经画出来了。

顺带解决了两件事：

- `html { background: #060608 }` 也内联了 —— 否则样式表下载完之前是一屏白闪。
- 这几 KB 内联 CSS 换来「首屏立刻有东西」，gzip 后约 1.1KB，比一次多余的网络往返便宜得多。

### 什么时候退场（含「最短一个循环」）

`src/lib/splash.ts` 的 `hideSplash()` 给 `#splash` 加 `.is-gone`（`opacity: 0`，0.32s），
`transitionend` 后 `remove()`，并带一个 700ms 定时兜底 —— 标签页在后台时 `transitionend`
可能不来，不兜底它就会一直挡着点击。

调用点在 `pages/Browse.tsx`，判据是**「第一份数据（`owners.json`）到齐」**，不是「React 挂载」：
挂载那一刻页面上还只有「正在雾中摸索…」一行字，动画多撑一会儿更连贯。
**出错也要退场**，否则用户会被永远挡在动画后面，看不到错误信息。

数据回得快时（本地、命中缓存，通常一两百毫秒）动画会被拦腰截断，看着像「闪了一下」。
所以 `hideSplash()` 卡了一个**最短展示时长 = 一个完整循环（2.4s）**：
起点来自 `index.html` 里的内联脚本记下的 `window.__splashT0 = performance.now()`
（HTML 解析到那里就开始计时，比在 JS 模块里取时间更准），不满一轮就等满再退。

⚠️ 代价是**每次首屏至少 2.4s**（包括缓存已经命中的情况）。想缩短就改 `splash.ts` 里的
`CYCLE_MS` 并同步改 `index.html` 里 `.sp-tally` 的时长；想完全去掉就设成 `0`。

### 想调的话

- 整轮时长：`.sp-tally` 与 `.sp-tally path` 上的 `2.4s`（两处要一起改，还要同步 `CYCLE_MS`）。
- 笔画间隔 / 快慢：五套 keyframes 里的百分比；「一间隔」目前是 8%（≈0.19s）。
- 标记尺寸：`.sp-tally` 的 `112 × 112`（viewBox 是 100×100，等比放大）。
- 笔画粗细与颜色：`stroke-width: 7` / `stroke: #e8e2d6`（骨白）、`stroke-linecap: butt`（平头，像刻出来的）。
- 竖线长短与间距：`d = "M19 10V92"` 这类 —— `M` 后的 y 是**顶端**（起点）、`V` 后的 y 是**下端**，
  所以四条是从上往下划的；想让某根反向生长，把两个 y 对调即可。
  x 之间差 21 就是间距。中间两根是 `M40 6V96`（两端各比左右长 4）。
- 斜线角度与长度：`d = "M-2 36.5L102 64.5"` —— dx 104、dy 28 ≈ 15°。
  想更陡就把 64.5 加大（36.5 减小），想更长就把 -2 / 102 往两边推
  （`.sp-tally` 是 `overflow: visible`，出画布也不会被裁）；方向反过来写 `M-2 64.5L102 36.5`。
- 雾的浓度：`.sp-fog` / `.sp-fog::after` 两层径向渐变的 alpha（0.17 / 0.14）。
- ⚠️ 雾的红是**写死的**，不是 `var(--accent)` —— 首帧时 `tokens.css` 还没加载、
  变量还没定义，而且阵营要到 hash 判完才知道。加载动画统一用游戏的招牌血红，不跟随阵营。

## 部署到 GitHub Pages

站点走 **Actions 构建 + 官方 Pages 部署**，不用「分支部署」——因为仓库根是工作区、
站点在 `app/` 子目录，而分支部署只支持 `/` 或 `/docs`；而且 Vite 产物不该提交进仓库。
（`gh-pages` 那条路已弃用：两套机制只能有一套管着 Pages，留着只会互相打架。）

### 域名：dbd.howerlin.top

- `howerlin.top` 是**用户站**（`howerrr.github.io` 仓库）的自定义域名，绑在你博客上，
  不能同时给这个站用 —— GitHub 的自定义域名只能绑**域名根**，也加不了路径。
- 所以本站用子域名 **`dbd.howerlin.top`**。
- 自定义域名是根路径 → **base 用默认的 `/`**，`VITE_BASE` 不需要设。

### 三件手动的事（各一次）

**1. DNS 加一条 CNAME**

| 类型 | 主机记录 | 值 |
|---|---|---|
| CNAME | `dbd` | `howerrr.github.io` |

**2. 仓库 Settings → Pages**

- **Source** 选 **GitHub Actions**（不是 Deploy from a branch）
- **Custom domain** 填 `dbd.howerlin.top` → Save（GitHub 会去校验 DNS）
- 等一会儿出现 **Enforce HTTPS** 勾上（证书签发可能要几分钟到几小时）

**3. 推代码**

```bash
git push
```

之后每次 push 到 `main` 都会自动：`npm ci` → 类型检查 → 单测 → 构建 → 产物自检 → 部署。

### 排查：`actions/configure-pages` 这一步失败

前面的类型检查、单测、构建都过了，却卡在 `Run actions/configure-pages@v5`，
报类似 `Get Pages site failed. Please verify that the repository has Pages enabled
and configured to build using GitHub Actions` —— **问题不在代码**，而是仓库设置。

这个 action 只做一件事：跟 GitHub 确认该仓库的 Pages 已启用、且 `build_type = workflow`。
仓库里 `has_pages` 已经是 `true` 但 Source 选的是 **Deploy from a branch** 时，
`build_type` 是 `legacy`，它就会失败。

去 **Settings → Pages → Build and deployment → Source** 改选 **GitHub Actions** 即可，
然后 Actions 页 → `Deploy to GitHub Pages` → **Run workflow** 重跑，不用改代码。

> 如果 Source 停在 `main / (root)`，`https://<user>.github.io/<repo>/` 会把**整个仓库源码**
> 当静态站发布出去（源码、package.json 全都能下载）。Cloudflare 那次就是这个症状。

### ⚠️ `app/public/CNAME` 不能删

内容是 `dbd.howerlin.top`，构建后成为 `dist/CNAME` 一起上传。

**Actions 部署必须这么做**：否则每次部署都会把 Settings 里的 Custom domain 清空，
域名反复掉（这是 Actions + 自定义域名最常见的坑）。

### 上线后核查

```bash
npm run verify:deploy https://dbd.howerlin.top/
```

检查**线上行为**：入口 JS/CSS 是否存在（能第一时间抓到「部署了源码而不是产物」）、
manifest 能否解析、不存在的 JSON 返回什么、抽样图片能否取到。
GitHub Pages 没有 `_headers`，所以缓存那几项会显示「缺少响应头」——那是预期内的。

### 上线前自检

```bash
npm run check   # typecheck + 单测 + 构建 + 产物自检
```

`verify-assets.mjs` 检查：每个 `/icons/` 引用都能在 dist 里找到真实文件、
CSS 里的 `url()` 都存在、没有 PNG 残留、配件索引条数与分包一致、
每个角色正好 3 个技能、入口资源与 manifest 都在产物里，并打印各页面的首次加载体积。
带 base 构建时也能跑（脚本会自动剥掉 `VITE_BASE` 前缀再比对文件）。

### 两个脚本别混用

| 脚本 | 用在哪 |
|---|---|
| `npm test` | CI。不带隔离 flag —— `--test-isolation` 在 Node 22 上叫 `--experimental-test-isolation`，写旧名会直接 `bad option` |
| `npm run test:one-process` | 受限环境（禁止 spawn 子进程）里用；默认隔离要 fork 子进程，那里会 `EPERM` |

### 顺带记一笔：`vite.config.ts` 需要 `@types/node`

`base` 从 `process.env.VITE_BASE` 读，没装 `@types/node` 就会
`TS2591: Cannot find name 'process'`，CI 的 typecheck 直接挂。
`tsconfig.json` 的 `types` 也要包含 `"node"`（那里只列了 `vite/client` 时会挡掉自动引入）。

## 附：之前用 Cloudflare 时踩的坑

（保留作参考。若哪天换回 Cloudflare，这些结论仍然有效。）

### 部署成 Worker 时的大坑

Cloudflare 的域名形如 `xxx.workers.dev` 说明项目是 **Worker** 而不是 Pages。
`wrangler.toml` 里必须用 **`[assets] directory`**：

```toml
[assets]
directory = "./dist"
```

如果误写成 Pages 专用的 `pages_build_output_dir = "dist"`，Worker 的 `wrangler deploy`
不认这个键、又没有 `main`，就会**把项目目录整个当静态资源传上去**。后果：

- 线上可以下载到 `/src/main.tsx`、`/package.json`、`/wrangler.toml`
- 首页返回**未构建的源码 `index.html`**（引用 `/src/main.tsx`），浏览器白屏
- 所有 `/assets/*`、`/data/*`、`/icons/*` 全部 404

`verify-deploy.mjs` 的第 [3] 项（入口 JS/CSS 是否存在）就是为了第一时间抓到这个。

### Cloudflare 专用的两个元文件

`public/_redirects`（SPA 回退 `/* → /index.html 200`）与 `public/_headers`（四档缓存）。
注意 `_redirects` 会把**不存在的 JSON 也回退成 index.html 并返回 200**，
所以 `api.ts` 不能只看 `res.ok`，必须校验 `content-type` 含 `json` —— 这个兜底在
GitHub Pages 下同样保留（那里是干净的 404，但 Vite dev server 仍会回退成 HTML）。

改用 GitHub Pages 后这两个文件已删除：Pages 不识别它们，而且会被当普通文件公开下载。
